## 1. `chat/` — active-stream cancellation doesn't survive horizontal scaling — DONE (2026-08-17)

**Where**: `backend/src/chat/service.py` — `ChatService._active_streams: dict[UUID, asyncio.Task]`, populated in `send_message`, read in `cancel_conversation`.

**The problem**: the registry mapping `conversation_id -> asyncio.Task` is in-process memory. `asyncio.Task.cancel()` only works on a Task living in the same Python process/event loop that created it. Today this is safe because `k8s/api-deployment.yaml` runs `replicas: 1` — every request for a conversation necessarily lands in the same pod. The moment `replicas` goes above 1, a `cancel_conversation` request that lands on a different pod than the one streaming the response will find nothing in its local `_active_streams` dict, treat it as "no active stream" (which is explicitly coded as a no-op, not an error), and return `200 {"status": "cancelling"}` while the other pod keeps streaming and billing tokens to completion. Silent failure — no exception, no log line, client is told cancellation happened when it didn't.

**Why it wasn't caught by the existing single-process decision**: `unit-of-work.md` (Application Design, Q1) already scopes the whole backend as one Python process, and the code comment on `_active_streams` cites that decision. But that decision was only explicitly stress-tested against `EventQueue` (see `unit-of-work-plan.md`'s Q1 discussion — "does single-process block testing the Redis Streams swap?"). Nobody asked the equivalent question for the Task registry, so it just inherited the single-process assumption without an interface or swap point the way `EventQueue` got one.

**Direction for the fix** (discussed at length, not yet designed in code):
- `asyncio.Task` itself can't be made distributed — that's not fixable, it's a language-level constraint. The fix isn't "swap the Task for something else," it's "stop depending on a Task handle being reachable across processes."
- Reuse the DB (`Conversation.state`, already exists, already flipped to `"cancelled"` — currently as a *result* of cancellation) as the cross-pod-visible signal instead. Flip the direction: `cancel_conversation` writes the cancel signal to Postgres immediately (before touching anything in-process); the streaming loop in `_run()` polls that signal once per token instead of waiting to be handed a `CancelledError` from outside.
- Unlike `EventQueue`'s Redis Streams swap, this doesn't need new infrastructure — Postgres is already shared across pods. `asyncio.Task` stays as purely local plumbing for running the streaming call concurrently within whichever pod holds the connection; it's just no longer the mechanism a *different* pod uses to signal cancellation.
- Once the mechanism is poll-based, it's the same shape as `EventQueue`: an interface, an in-process/DB-backed default, and (if ever needed) a swappable faster backend later.

**What was actually implemented**: `_active_streams`/`task.cancel()` kept as-is for the same-pod fast path (still instant, zero regression for the currently-deployed `replicas: 1` case). Added on top: `cancel_conversation` now writes `update_state(conversation_id, "cancelled")` to Postgres unconditionally, before touching the local registry — that write is the cross-pod-visible signal. `_run()`'s streaming loop polls `ConversationRepository.get()` at most once per `_cancellation_poll_interval` (constructor param, default 0.5s, wall-clock throttled so a fast token stream doesn't turn into a DB query per token) and, if it sees `state == "cancelled"`, calls `asyncio.current_task().cancel()` — self-cancellation, not a parallel code path, so it flows through the exact same `except asyncio.CancelledError` handling (partial content persisted, `InstrumentedProvider`'s own cancellation `LogEvent` still fires correctly) that the same-pod path already used. New test: `test_cancel_from_a_different_pod_is_picked_up_by_the_db_poll` in `backend/tests/chat/test_service.py` — flips `Conversation.state` directly via the shared repository, deliberately never touching `_active_streams` or `cancel_conversation`, to prove only the poll could have caused the resulting cancellation. Full backend suite (60 passed, 8 pre-existing DB-integration skips) and frontend suite both green after the change.

## 2. `ingestion/` — dead-letter fallback logging is also single-pod — CLOSED, different fix than item 1 (2026-08-17)

**Where**: `backend/src/ingestion/worker.py` — `IngestionWorker._record_failure`, the `except Exception: logger.critical(...)` fallback that runs if writing a `FailedLogEvent` to the DB *also* fails.

**Re-assessed**: this doesn't get item 1's treatment. Item 1 was fixable because Postgres itself was healthy and reachable — only the in-memory registry failed to cross pods. This failure mode only triggers once *both* the primary `LogRecord` insert and the dead-letter insert have already failed, meaning Postgres itself is unreachable — there's no cross-pod-visible store left to signal through, so a distributed-systems fix wouldn't add anything real. Decided to leave the single-pod-log boundary as-is (it matches the already-documented "no further fallback layers beyond that" decision in the Unit 3 business-logic-model).

**What was actually wrong, and fixed instead**: re-reading the code turned up a real, independent bug — the critical log line was `logger.critical("Failed to dead-letter event and failed to record failure", exc_info=True)`. `exc_info=True` only captures the exception *currently in flight*, which at that point is the dead-letter insert's own failure — not the original pipeline-stage exception (`exc`, the parameter) that caused `_record_failure` to be called in the first place. So the one log line meant to be the last-resort signal when everything else has failed didn't actually say what broke, which stage, or which event. Fixed by explicitly including `stage`, `event.model`, `event.provider`, `event.conversation_id`, `event.session_id`, and the original `exc` in the log message, alongside `exc_info=True` for the dead-letter failure's own traceback. `test_dead_letter_write_failure_falls_back_to_logging_not_a_crash` in `backend/tests/ingestion/test_worker.py` extended to assert the original context actually appears in the log output. Full backend suite green (60 passed, 8 pre-existing skips).

## 3. `auth/` — session cookie missing `secure=True` — DONE (2026-08-17)

**Where**: `backend/src/api/auth_router.py` — `response.set_cookie(key=SESSION_COOKIE_NAME, value=..., httponly=True, samesite="lax")`.

**The problem**: no `secure=True` flag, so the cookie isn't marked HTTPS-only at the cookie level. Currently harmless in practice since the live deployment is HTTPS-only via cert-manager, but it's not enforced by the cookie itself — if the app were ever reachable over plain HTTP (e.g. local port-forward, a future non-TLS environment), the session cookie would still be sent.

**Direction**: one-line fix, `secure=True` added to the `set_cookie` call. Should probably be conditional on environment (`secure=not DEBUG` or similar) so local dev over `http://localhost` still works — check this before just flipping it on unconditionally.

**What was actually implemented**: added `auth/cookies.py::session_cookie_is_secure()` — reads `SESSION_COOKIE_SECURE` from the environment live (not cached at import, so tests can `monkeypatch` it), defaults to secure-by-default (`True`) if unset, so a new environment that forgets to configure this gets the *safe* behavior rather than silently repeating this exact bug. Applied to both `set_cookie` (login) and `delete_cookie` (logout, for consistent clearing — Starlette's `delete_cookie` accepts matching `secure`/`httponly`/`samesite`). `SESSION_COOKIE_SECURE=false` added to `docker-compose.yml`'s `api` service and `backend/.env.example` so local dev (always plain HTTP) keeps working without any code change; `k8s/api-deployment.yaml` needs no change since it doesn't set the var and the real deployment is HTTPS. Caught a real thing while testing: `TestClient` correctly refused to send the `Secure` cookie back over its fake `http://testserver` connection, breaking 2 existing tests — same failure mode a real browser would show on plain HTTP, so it's proof the flag works, not a bug. Fixed by adding an autouse `monkeypatch.setenv("SESSION_COOKIE_SECURE", "false")` fixture to `tests/api/test_auth_router.py` (mirrors the local-dev opt-out), plus two new tests asserting the header explicitly does/doesn't carry `Secure` in each mode. Full backend suite green (62 passed, 8 pre-existing skips).

## 4. `db/` — deliberately dead method left in `UserRepository` — DONE (2026-08-17)

**Where**: `backend/src/db/user_repository.py` — `get_or_create_seed_user()`, docstring says *"No longer called by anything once Unit 5 lands; left in the interface as historical record rather than removed."*

**The problem**: not a bug — a judgment call worth revisiting for a real submission. Keeping superseded interface methods around as "historical record" makes sense mid-build (shows the evolution), but for a final submission it reads as dead code a reviewer has to figure out is intentional.

**Direction**: decide whether to remove it (and its `SqlAlchemyUserRepository` implementation) before submission, or keep it with a clearer comment explaining it's intentionally retained. Low effort either way — do this one quickly alongside whichever other item is being worked.

**What was actually implemented**: confirmed via grep it was never called from any production code path (only from tests and the interface/implementation definitions themselves) — removed it entirely, rather than keeping it with a clearer comment. Removed the abstract method + docstring references from `db/user_repository.py`, the implementation + now-unused `SEED_USERNAME` constant from `db/sqlalchemy_user_repository.py`, and the matching override from `tests/auth/doubles.py`'s `FakeUserRepository`. Turned out to be more than a one-liner: `tests/db/test_sqlalchemy_repositories.py` (the real-Postgres integration suite) used it in 5 places specifically *because* it was safely re-callable across tests with no per-test DB cleanup (check-then-create on a fixed username). Replaced those call sites with `user_repo.create_user(f"test-{uuid4()}")` — a fresh, guaranteed-unique username per call, which doesn't need the check-then-create dance since it's not reusing anything — and deleted `test_seed_user_is_idempotent` outright, since it tested behavior that no longer exists. Verified against a real local Postgres (`docker-compose up -d postgres` + `alembic upgrade head`), including running the integration suite **twice in a row** against the same accumulating database with no cleanup between runs, to specifically prove the new unique-username approach doesn't hit the `username` unique-constraint the old idempotent method was designed around. All 7 passed both times. Full suite: 62 passed, 7 skipped (was 8 — one fewer test now that `test_seed_user_is_idempotent` is gone, not a new failure).

## 5. `frontend/` — unmount cleanup aborts the local read but doesn't cancel the backend call — CLOSED, intentional, not a gap (2026-08-17)

**Where**: `frontend/src/hooks/useChatStream.ts` — the `useEffect` cleanup on unmount only calls `abortControllerRef.current?.abort()`, unlike the `cancel()` function which also calls `cancelConversation(conversationId)`.

**The problem**: if a user navigates away mid-stream (not via the Cancel button), the frontend stops reading, but the backend keeps streaming from Gemini and billing tokens to completion — same asymmetry as `cancel()` is designed to avoid, just not applied to the unmount path.

**Direction**: decide if this is intentional (maybe: navigating away isn't necessarily "cancel this conversation," the user might come back to it) or a gap. If it should cancel, the unmount cleanup needs the same two-call pattern `cancel()` already uses.

**Decision**: closed with no code change, after re-examining what actually happens today. `_run()` (the background task doing the real Gemini streaming + eventual DB persist) is completely independent of whether the client keeps reading - aborting the fetch only stops *this browser tab* from reading further SSE bytes, it doesn't touch `_run()`. So today, navigating away mid-stream doesn't lose or corrupt anything: the response keeps generating server-side and gets persisted normally, and resuming that conversation later shows the complete response. There's no resource leak or correctness bug here, only a cost tradeoff (Gemini tokens spent on a response nobody was watching in the moment) - and letting it keep running matches how mainstream chat products behave (e.g. ChatGPT continues generating and shows the finished result when you come back), which is arguably the better default: making unmount also cancel would mean briefly clicking to the conversation list or another conversation and back could truncate an in-progress response, an easier way to lose content by accident than the deliberate Cancel button. Confirmed with the user as a product decision rather than deciding unilaterally - explicitly choosing to keep the current behavior.
